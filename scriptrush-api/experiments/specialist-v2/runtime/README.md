# Executable Full Hub gate

This evaluates the **actual rendered Luau handlers**, rather than treating a feature ID or a callback string as proof of function. It uses the already installed official Luau 0.742 CLI and extends the existing closed Roblox mock with the original, owned fictional fixture objects from each case's `gameEvidence`. The model does not receive expected answers or this harness.

```powershell
node --experimental-strip-types --test experiments/specialist-v2/runtime/runtime.test.ts
node --experimental-strip-types experiments/specialist-v2/runtime/run.ts test-results/specialist-v2/dataset/test.jsonl test-results/specialist-v2/predictions.jsonl test-results/specialist-v2/runtime-report.json
```

Set `LUAU_BIN` to an existing official Luau executable if the workspace QA binary is not present. The harness never installs or downloads executables. Output JSON, generated source and executable wrappers are written only under ignored `test-results/specialist-v2/`.

The gate checks independent controls for speed, jump, camera FOV, local brightness, landmark highlight, camera aim, live currency notifications, existing journal visibility, existing HUD state, rejoin requests and palette switching. It also checks exact window dimensions, corner radius, title or absence, fonts, tab labels/order/navigation/visibility, active colors, drag, minimize/restore, close and cleanup. Currency is changed between clicks to detect hardcoded or stale values. Invalid numeric inputs and both boundaries are exercised. The character and Humanoid are replaced before another speed/jump Apply; the old character is destroyed. The landmark and camera origin move before a second focus click. Actual original brightness varies by fixture after the supplied evidence snapshot, exercising restoration of live state instead of a memorized training value. Brightness, markers and HUD are left changed before closing to exercise their cleanup callbacks. Negative tests explicitly reject stale Humanoids, landmark coordinates and brightness, along with no-op callbacks.

Candidate globals expose no host filesystem, networking, OS, `require`, `loadstring`, `getfenv`, raw table access or reflection. Each process receives a minimal OS environment without provider credentials, has a six-second deadline and a bounded output buffer. The host compiles the quoted candidate with its own `loadstring` into a **separate chunk**, then applies the closed environment; `loadstring` is never exposed to that environment. This compilation boundary is necessary because `setfenv` alone does not hide captured lexical locals when generated code is interpolated into a harness function. Tests reject direct access to host expected answers, feature bindings, assertion tables and instance lists, along with an attempted syntax escape from an enclosing function. The renderer's fresh service table uses restricted `setmetatable`; existing mock instances cannot have their metatables replaced.

This is **mock runtime validation**, not certification of a live Roblox game. It does not verify engine pixels, font glyph metrics, actual teleport delivery, server permissions, real game object availability or features beyond the explicitly assessed fixture actions. A real game needs its own evidence and runtime tests. Schema-invalid, missing, no-op and UI-mismatched candidates cannot pass the combined gate. A passing reference self-test validates the harness only; it is not a model benchmark result.

The mock accepts existing service aliases (`game.Players`), Workspace child member lookup and the documented [`CFrame.new(position, target)` overload](https://create.roblox.com/docs/reference/engine/datatypes/CFrame), including translation-only constructors with default negative-Z orientation. Targeted tests exercise alternate valid syntax and a moved target while retaining missing-child, wrong-currency, wrong-target and cleanup failures. These tests compare observed state in the finite mock; its Lua table implementation and vector equality are not identical to Roblox engine objects. The original developer evaluation report is preserved separately when corrected mock semantics require re-scoring unchanged model outputs.
